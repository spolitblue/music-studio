# 制乐 Music Studio

一个用 **Python + PySide6** 写的音乐制作软件。所有声音都由代码实时合成/离线渲染，
不依赖任何音色采样包；界面是 **iOS 风的玻璃材质**，图标取自 **Twemoji**。

**现在就能用**：双击 `run.bat`，打开即是一首 8 小节的示范曲，按空格就能听到声音。

---

## 快速开始

```powershell
# 方式一：双击 run.bat（首次会自动建虚拟环境并装依赖，约 250MB，只需一次）

# 方式二：手动
py -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python -m app.main

# 打开空工程 / 已有工程
.venv\Scripts\python -m app.main --empty
.venv\Scripts\python -m app.main 我的曲子.musicproj.json
```

### 无头复刻（命令行）

界面上「AI 扒谱·复刻」页的那条流程，命令行里也走同一套代码：

```powershell
# 1) 手上是 mp3 就直接给（PySide6 自带的 QtMultimedia 解码，不需要装 ffmpeg）
#    —— 也可以先转成 WAV 再喂进去
.venv\Scripts\python tools\decode_audio.py 参考.mp3 参考.wav

# 2) 量指纹 → 生成 → 渲染 → 导出 WAV / MIDI / 工程 JSON
.venv\Scripts\python tools\replicate_cli.py 参考.wav --out _out\demo --seeds 3
.venv\Scripts\python tools\replicate_cli.py 参考.mp3 --out _out\demo --target-seconds 200
```

产物：指纹（json/txt）、每个种子一套 `.wav` + `.mid` + `.musicproj.json`（可直接在界面里打开继续改）。
`--target-seconds` 会把多段（每段换种子，和弦走向随之改变）接成一首长曲 —— 段落编排由脚本负责，
音符仍然全部由编曲助手生成。

## 音序器的操作方式

最要紧的一条是**边写边听** —— 听不到自己写的是什么，编曲就是盲写。

### 鼠标

| 操作 | 效果 |
|---|---|
| 左键点空格 | 加音符，**并立刻试听** |
| 左键点已有音符 | 删掉它 |
| 左键按住拖动 | 连续刷音符（**经过已有音符不会擦掉它**）|
| 右键 | 擦除 |
| **Shift + 上下拖** | 改力度（横向不动）|
| **拖音符右缘** | 改时值 |
| **Alt + 拖动** | 框选 |
| 滚轮 / Shift+滚轮 | 纵向 / 横向滚动 |
| **Ctrl + 滚轮** | 缩放（以鼠标位置为锚点，画面不会跑掉）|

### 键盘

`Delete` 删除选中（无选区则清空当前行）· `Ctrl+A` 全选 · `Ctrl+C/V` 复制粘贴（锚在播放头）·
`Ctrl+D` 复制本小节到下一小节 · `Ctrl+Z/Y` 撤销重做 · `←/→` 挪播放头一步 · `Esc` 取消选区

### 几个不显眼但决定手感的取舍

* **一整笔拖动只占一步撤销**。拖动会改几十个音符，按次压栈的话撤销要按几十下才退得回去。
  做法是网格在**按下那一刻**发一次 `editStarted`，拖动全程共用这一个撤销点。
* **撤销栈存整份工程快照**而不是增量操作。示范曲 JSON 才 45KB，整份存比"记录每个操作
  及其逆操作"简单得多，也不会因为某条编辑路径忘了记录而漏掉撤销点。
* **试听走常驻输出流**（`BlipPlayer` + 待播队列），不是每次点都新开一条流 ——
  后者有几十毫秒延迟且容易失败，而试听是跟着鼠标点击走的，慢了整个流程就断了。
* **选区用「泳道区间 × 步区间」表示**，不记录音符对象。撤销/重做会重建整个工程，
  按对象记的选区会全部失效。
* **悬停读数不用 tooltip**。tooltip 要悬停半秒才弹还挡视线；编曲需要的是一眼能扫到的即时反馈。

## 关于「并行开发」这件事

后面 5 个模块（钢琴卷帘 / 鼓机 / 混音台 / 效果器链 / 编曲助手）是**并行**做的：
每个模块一个独立 agent 负责实现，**再各派一个独立 agent 去证伪**。

这不是为了快，是为了两件具体的事：

1. **防止「声称完成」**。实现 agent 和复核 agent 是两个上下文，复核者只看代码和
   实际运行结果，不看实现者的自述。实测抓到 5 个模块**全部**存在实现者自己测试漏掉的
   真缺陷 —— 包括一个「拖音符改音高后不发 edited，导致听到的还是旧音」的功能性 bug，
   而实现者的测试是 99 项全绿的。
2. **防止单会话记忆漂移**。一条长会话里，早期的设计决策会随着上下文增长而失真。
   隔离的 agent 没有这个问题，但代价是**它什么都不知道** —— 所以必须先有一份
   `docs/MODULE_CONTRACT.md`，把接口、可用设施、禁止事项全部写死。
   契约没写清楚的地方，agent 就会各自发明一套。

复核抓到的缺陷里有一条特别值得记：

> **`push_undo` 压在改动之后** —— 三个模块**独立地**犯了同一个错。
> Qt 的天然写法是「改数据 → 发信号」，而撤销点必须压在改之前。
> 三个 agent 各自掉进同一个坑，说明**是契约漏了这条，不是它们不细心**。
> 这类系统性错误只能靠「多个独立样本撞同一个墙」暴露出来。

## 几个关键设计决定

### 玻璃：真的会折射，且背景真透明

参考的是 Minecraft 模组 **LumaGlass / 液态玻璃** 那种质感，而不是浏览器的
`backdrop-filter` 毛玻璃。核心差别在**边缘折射** —— 玻璃的圆角边缘像一块厚透镜，
把轮廓**外面**的画面往里掰弯，于是边框附近出现一条明亮、被挤压变形的光带。

**表面处理做成可切换档位**（`app/theme.py`），换档只需改 `theme.finish = theme.FROSTED`：

| | 光面（默认） | 磨砂 |
|---|---|---|
| 模糊 | 2.5（几乎不糊） | 16（看不清背后） |
| 凝霜 | 0.045 | 0.17 |
| 高光 | 窄而锐的斜向镜面反光 | 柔和漫射 |
| 噪点 | 几乎无（表面光滑） | 有（模拟粗糙度） |

实现分五步（`app/widgets/liquid.py`）：

1. 求圆角矩形的**有符号距离场**（SDF）
2. 对 SDF 求梯度得到**边缘法线**
3. 法线 ×「靠边越强」的权重 = **折射位移图**
4. 用位移图对背景做**双线性重映射**
5. 叠凝霜/饱和/聚光，alpha 按 rim 从「内部透明」过渡到「边缘不透明」

有个容易写错的关键点：**模糊与重映射必须在「带余量的整块」上做，最后才裁出面板**。
先裁再算的话，采样会被钳在面板边界内 —— 效果就退化成「面板自己的画面被扭曲」，
而不是真的把外界的画面吸进来。

#### 背景真透明带来的三个连锁问题

窗口背景是**真透明**的（桌面透过系统亚克力直接透上来，我们不自绘底图）。这逼出三件事：

1. **折射没有像素可读**。桌面是 DWM 合成的，Qt 拿不到。解决办法是
   `capture_desktop()`：把窗口临时透明化 → 让 DWM 合成一帧 → 截屏 → 恢复。
   玻璃折射的就是用户**自己的壁纸**。代价是那一瞬间窗口会闪，所以只放在启动和
   移动/缩放停手之后（防抖 420ms），**绝不进逐帧路径**。截不到时回落到自绘散景。
2. **面板内部不能画贴图**。把截下来的桌面以满不透明度画上去，看着像玻璃，
   实际是张贴图 —— 真实桌面根本透不过来。所以 `interior_alpha = 0.30`：
   **内部透明（让真实桌面透过），只有边缘那一圈画折射**。
3. **亮壁纸会把白字淹掉**。所以暗幕**自适应**：读面板背后画面的亮度
   （取 75 分位而非均值 —— 决定可读性的是最亮的那块），亮则多压、暗则保持通透。

实测：窗口半透明像素占 **88.3%**，不透明仅 4.9%。

性能上做了两处结构性优化：

* **只重映射边缘一圈**。面板内部 `rim = 0` ⇒ 位移恒为 0 ⇒ 重映射是恒等变换，
  算了白算。边缘带面积只有 `周长 × 带宽`，对 1240×96 的面板是 6 倍差距。
* **背景只模糊一次**。所有面板共用同一张预模糊图。
  1240×96 的面板：含模糊 52ms → 预模糊 12ms。

结果按控件缓存，尺寸不变就一直复用。

窗口仍然是无边框的（系统标题栏会挡住材质）。拖拽/缩放用 Qt 6 的
`QWindow.startSystemMove / startSystemResize` 交还窗口管理器，
**贴边、双击最大化、多显示器缩放全部原生可用**。
系统关掉「透明效果」时亚克力会静默失效，`win_glass.transparency_enabled()`
会先查这个开关并降级为自绘玻璃。

### 材质分三层 + 烟熏玻璃

侧边栏（结构）→ 卡片（内容）→ 按钮芯片（可交互），每层不透明度差 ≥ 0.10。
Apple 的设计文档明确警告「绝不要在浅色半透明上叠浅色半透明」，所以这三层是硬约束。
每个玻璃面都带 **1px 顶部高光边**、**粗亮轮廓**与 **微观噪点** ——
少了这几样，玻璃立刻退化成塑料板。

承载文字的面板（轨道行、母带卡、走带条）额外叠一层**暗色染色**：
凝霜后的玻璃偏亮，白字直接压上去对比度只有 3:1 上下；加一层烟熏后实测
**11:1**（WCAG AA 要求 4.5:1），视觉上也更沉、层次更清楚 ——
正是设计文档里「调暗以聚焦」那条。

### 弹簧是物理仿真，不是缓动曲线

`motion.py` 用半隐式欧拉积分阻尼谐振子。这样做的关键收益是**可中断性**：
对同一属性再次发起动画时，新弹簧从**当前位置**出发并**继承当前速度**。
阶跃响应曲线做不到这点（它每次都从 v=0 重新开始）。

顺带避开了 PySide6 6.9 的一个缺陷：`QEasingCurve` 在 `BezierSpline` 模式下
析构即崩（与动画 parent、曲线段数都无关）。详见 `Spring.to_easing` 的注释。

### 音频：离线渲染 + 流式回放

PortAudio 的回调绝不能做耗时操作。所以播放路径是：

```
改一个音符 → 防抖 450ms → 后台线程离线渲染整首 → 装载 → 流式回放
```

回调里只做「拷贝 + 推进游标」，零计算、零分配。代价是改一个音要重渲染整首 ——
8 小节的曲子约 5 秒（4.5× 实时），换来的是播放绝对稳定、不会有实时合成的爆音。

### DSP 里的三个"作弊"

1. **带限波表**：锯齿/方波用加法合成预生成一倍频程一档的波形表（mip-map），
   按基频选谐波数不超奈奎斯特的那张。非谐波能量 **−101dB** 以下 ——
   而不带限的 naive 锯齿是 **−11.5dB**（明显可闻的金属味）。
2. **IIR 走 FFT**：滤波器/延迟/混响都是线性时不变系统，先求冲激响应再 FFT 卷积。
   数学上与原递推完全等价，代价从 O(N·阶数) 降到 O(N log N)。
3. **控制率与音频率分离**：时变滤波器的系数每 32 个样本更新一次再线性插值，
   省掉每样本一次三角函数，扫频照样平滑。

## 已知问题（如实记录，未修）

这些是复核与集成阶段发现、但**有意留到后续处理**的问题。写下来是为了让它们
是「已知项」而不是「没这回事」。

1. **渲染在途时关窗要等 5.7 秒**。取消是协作式的，只在轨道/音符边界生效；
   遇到带效果链的长轨道（实测主旋律轨单轨 2.6s）就得等它跑完一段。
   实测 shutdown 耗时 5.7s，逼近 6s 上限 —— 一旦超时线程就收不了工，
   进程退出时会被 Qt `__fastfail` 带走（退出码 `0xC0000409`，而测试的 OK/FAIL 全绿）。
   根治要么把 `render_track` 做成可中断的，要么把整轨渲染挪进可抢占的线程池。
2. **混音台的参考电平分析在 GUI 线程上跑**，单轨实测 0.19~2.61s、5 轨累计约 5.3s
   （贵在轨道效果链）。现在是「两条轨道之间让事件循环喘 16ms」的串行排队，
   界面能出但表是逐条亮起来的。要真正流畅得挪到后台线程。
3. **钢琴卷帘**：长音符拖动时的占位判定只比对目标音高的起始步 ——
   把一个长音符拖到与另一个长音符**中段**重叠的位置不会被挡住。
4. **`GlassSurface` 带一个从不 emit 的 `clicked` 信号** —— 子类忘了接就是
   「点了没反应」的陷阱。编曲助手页面的标题徽标就是这么来的（现已改成纯装饰控件）。
5. **`MainWindow` 构造失败无法降级**：页面构造抛 Python 异常时 `try/except` 能兜住，
   但若半构造的 QWidget 已经把 QThread 带起来，Qt 的 fail-fast（`0xC0000409`）
   Python 拦不住，会带走整个进程。实测：连续 7 个页面构造失败后进程整体挂掉。

## 两个必须记住的坑

### 1. 批处理文件必须是 CRLF 换行

`run.bat` / `run_tests.bat` 用 LF 换行时，`cmd.exe` 会把行从任意位置劈开，
851 字节的脚本变成十几条 `'orlevel' 不是内部或外部命令`，双击后窗口一闪就没 ——
用户看到的只是"这个文件打不开"。

而现代编辑器/write 工具默认输出 LF，所以这个坑很容易悄悄复发。两道防线：

```powershell
python tools\fix_bat_eol.py --check   # 检查
python tools\fix_bat_eol.py           # 修复
```

以及 `tests/test_design.py` 第 7 节会在每次跑测试时断言所有 `.bat` 都是 CRLF。

### 2. PySide6 的两处参数类型陷阱

* `QObject.property()` 只接受 **str**，`QPropertyAnimation` 只接受 **bytes**
  —— 正好相反。类型传错在 PySide6 6.9 上不报错，而是**访问违例崩进程**。
* 现在弹簧已经不走 `QPropertyAnimation` 了（改用物理积分，见上文），
  所以只剩前者需要注意。

类似的：`QEasingCurve` 一旦通过 `addCubicBezierSegment` 变成 `BezierSpline`，
析构时会崩 —— 而且动画**运行期间一切正常**（数值、过冲都对），只在释放时炸，
单看功能测试完全发现不了。
